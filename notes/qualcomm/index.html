    One SoC,
    six places to run a tensor

    A Snapdragon or Dragonwing chip gives you a CPU, a GPU, an NPU, a DSP and a micro-power NPU. Qualcomm's software stack is the set of tools that decides which one runs your model and how well. This guide walks the whole path, from a PyTorch checkpoint to a tuned inference loop on the NPU.

    train → ONNX → AIMET (quantize) → qairt-converter (DLC) → context binary (per SoC) → QNN runtime → HTP / GPU / CPU / LPAI

    Module 02

    The silicon: six backends

    A QNN backend is one shared library that drives one piece of hardware. Click a block on the floorplan.

    ISP · modem · memory
    FastRPC: the CPU ↔ DSP call bridge every NPU job crosses

    NPU, HTP and DSP are not three chips. "NPU" is the marketing name. "HTP" (Hexagon Tensor Processor) is the QNN backend name for it. Physically it lives in the compute DSP subsystem (cDSP / NSP). In SNPE you still select it with the runtime named DSP. The QNN DSP backend is a different thing: older Hexagon cores without the tensor accelerator.

    Inside the Hexagon NPU

    Scalar cores

    Control flow, glue, ops with no vector kernel. Slow path.

    HVX (vector)

    1024-bit SIMD. Runs many element-wise and non-conv ops. You reserve HVX threads per graph (default 4).

    HMX (tensor)

    Matrix engine for conv and matmul. This is where the TOPS come from. Works on fixed-point and, on newer chips, FP16.

    VTCM is a small, fast on-chip memory the tensor engine works from. Bigger VTCM per graph means fewer tile shuffles, but it is shared between all graphs on that core. Default is 4 MB.

    HTP generations

    ArchTypical chipsWhat changed
    v68Snapdragon 888, QCS6490 (RB3 Gen 2)First HTP. Quantized only.
    v698 Gen 1FP16 arrives on select SoCs.
    v738 Gen 2, QCS8550, X Elite, QCS9100 / SA8775PWeight sharing across graphs. Workhorse for LLMs.

    Chip-to-arch mapping is from memory of public material. Confirm yours in the SDK's supported-devices page before you set dsp_arch.

    Module 03

    Precision & quantization

    Precision decides the backend more than anything else. A float model cannot use most of the NPU. A badly quantized model uses it and gives wrong answers.

    BackendFP32FP16INT8INT16 act.4-bit weightsNotes
    CPUFP32 and quantized 8-bit from the same library.
    GPUModes: FP32, FP16, hybrid (FP16 tensors, FP32 accumulators).
    HTPINT8/INT16 on every SoC. FP16 on select SoCs. BF16 on Windows v81+. FP32 graphs run as FP16 when relaxed precision is on.
    DSP8-bit fixed point.
    LPAIQuantized only. Float models are rejected.
    HTA16-bit activations only with 8-bit weights.
    supported conditional not supported

    Reading the notation

    • w8a8: 8-bit weights, 8-bit activations. Fastest, least robust.
    • w8a16: the default for transformers and anything with wide activation ranges.
    • w4a16: LLM weights. Needs block-wise tricks (LPBQ) to hold accuracy.
    • ExecuTorch writes it the other way round: 16a8w.
    • Weights are usually symmetric and per-channel. Activations are asymmetric and per-tensor.

    AIMET, in order of effort

    • Calibrate: QuantizationSimModel + compute_encodings on a few hundred samples.
    • Free fixes: batch-norm folding, cross-layer equalization.
    • Better rounding: AdaRound, Sequential MSE, BN re-estimation.
    • Find the bad layer: QuantAnalyzer, then mixed precision (manual or automatic) to lift only those layers to 16-bit.
    • Last resort: QAT. For LLMs: LPBQ, OmniQuant, SpinQuant.
    • Export gives ONNX + an .encodings JSON. Feed that to the converter with --quantization_overrides.

    Three ways to quantize, pick one. AIMET (most control), qairt-quantizer on a DLC (quickest, fewer algorithms), or an AI Hub quantize job (AIMET-ONNX run for you in the cloud). Do not stack them.

    Module 04

    Op support explorer

    QNN defines well over a hundred ops. Each backend implements a subset, and each op has its own rank, datatype and parameter limits. Search an op, or filter to see what a backend lacks.

    listed in Qualcomm's table or backend supplement expected in current SDKs, not checked here not supported? not checked

    How far to trust this table. Rows up to ElementWiseNeg come from Qualcomm's supported-operations table, and the whole GPU and DSP columns come from their op supplements (docs published Aug 2026). I could not load the rest of the HTP, LPAI and HTA columns, so those show hollow dots or "?". Before you design around an op, open SupportedOps and the HTP supplement for your SDK version.

    Why a "supported" op still falls back

    • Rank. Most HTP ops stop at 4D or 5D. A 6D reshape in a window-attention block breaks the partition.
    • Datatype. int64 indices, bool masks and float64 are common ONNX leftovers. Truncate or cast them before conversion.
    • Dynamic shapes. Backends want static dims. The GPU backend states it plainly: variable input and output dimensions are not supported.
    • Parameter limits. Example from the ORT QNN EP: Gather needs positive indices, LpNormalization only p = 2, MatMul on HTP only for specific uint8/uint16 input pairs.
    • Precision column. An op can exist for INT8 and not for FP16, or the other way round.

    One fallback op in the middle of a graph costs two FastRPC crossings plus a dequantize and a quantize. Three small NPU islands are usually slower than running the whole thing on the GPU.

    Module 05

    Which backend, and why

    Answer four questions. The recommendation updates as you click.

    Why some models go to the NPU and others to the GPU

    NPU wins when
    • The model is quantized and the graph is static.
    • Conv and matmul dominate, so HMX does the work.
    • You care about energy per inference or sustained thermals.
    • You can build the context binary offline.
    GPU wins when
    • The model is float and quantization hurts accuracy (depth, flow, some diffusion parts, regression heads).
    • The op set is exotic or shapes change.
    • The data is already on the GPU (camera, render, OpenCL pipeline).
    • The NPU is busy with a higher-priority model.
    WorkloadUsual homeReason
    Detector / segmenter (YOLO, DeepLab)HTP w8a8 / w8a16Conv-heavy, quantizes well.
    ViT, DETR, VLA vision towerHTP w8a16LayerNorm and softmax need 16-bit activations.
    LLM / VLM decoderHTP w4a16 via GenieSplit into several context binaries, KV cache handled by Genie.
    Monocular depth, super-resolution in floatGPU FP16Accuracy-sensitive, no calibration needed.
    NMS, tracker, pre/post-processingCPUBranchy, dynamic sizes, tiny compute.
    Keyword spotting, tactile or IMU classifierLPAIRuns while the application processor sleeps.
    Small MLP distilled from a random forestCPU or LPAIRPC overhead exceeds the compute on HTP. LPAI if it must be always-on.
    Module 06

    End to end: checkpoint to device

    Two lanes reach the same artifacts. The SDK lane runs on your x86 Linux box and in CI. The AI Hub lane runs in Qualcomm's cloud on real phones and boards.

    Changed in Sept 2026: AI Hub Workbench no longer compiles straight to a QNN context binary. Compile to qnn_dlc, then run a link job to get the binary.

    The three files you will ship

    DLC

    Graph + weights + encodings. Portable across SoCs and backends. Prepared on device at load, which is slow on HTP.

    Context binary

    Already compiled for one HTP arch and one QAIRT version. Loads fast. Rebuild it when either changes.

    Wrapper model

    *_ctx.onnx for ONNX Runtime or .pte for ExecuTorch. A thin shell that points at, or embeds, the context binary.

    About "assigning cores" on the NPU. You do not pin NPU work to cores the way you pin CPU threads. You choose a device and core on multi-NPU chips, reserve HVX threads and VTCM per graph, and set priority. The Hexagon RTOS schedules the rest.

    • Feed it without copies. Allocate with rpcmem_alloc (DMA-BUF), register with QnnMem_register, set the tensor memType to memhandle. The NPU reads the camera buffer in place.
      • 
    
    • Skip CPU quantization. Keep I/O tensors in their native uint8/uint16 type and fill them yourself with q = round(x / scale) - offset.
      • 
    
    • Switch behaviour live. Several graphs can sit in one context and share weights (up to 64 per context, v73+). Pick one per call. LoRA adapters can be applied to a loaded context. ORT exposes ep.dynamic.workload_type to drop priority at runtime.
      • 
    
    • See inside. No mid-graph tensor access on HTP at runtime. Use --profiling_level detailed for per-op time, optrace for a timeline, and debug builds that mark every layer as an output for value dumps.
      • 
    
    • Watch the DSP. adb shell sysMonApp getLoad-style queries and Snapdragon Profiler show cDSP utilisation and clocks. CPU tools will not show NPU load.

    Module 08
    Debugging & the traps everyone hits
    
  
    
    
    When it will not load
      
      
    • Version skew. Context binary, libQnnHtp.so, the stub and the libQnnHtpV73Skel.so on the DSP must come from the same QAIRT release.
      • 
      
    • Skel not found. Set ADSP_LIBRARY_PATH to the folder holding the skel. On Android declare libcdsprpc.so with uses-native-library.
      • 
      
    • Wrong arch. A v75 binary will not run on a v73 chip.
      • 
      
    • Too big. One HTP session has a limited address space. LLMs are split into several binaries for this reason.
      • 
    
    
    
    When it is slow
      
      
    • Fallback islands. Check which compute unit each layer landed on before reading any latency number.
      • 
      
    • On-device prepare. Loading a DLC on HTP compiles it on the phone. Ship a context binary.
      • 
      
    • Cold NPU. First inference after idle pays wake-up. Use burst plus RPC polling, or accept it.
      • 
      
    • Layout transposes. NCHW models gain transposes at I/O. Feed NHWC.
      • 
      
    • CPU quant/dequant. Float I/O on a quantized graph converts every frame on the CPU.
      • 
    
    
    
    When it is wrong
      
      
    • Run the quantized DLC on the CPU backend first. If it is already wrong, it is quantization, not the NPU.
      • 
      
    • Compare layer by layer with qnn-accuracy-debugger.
      • 
      
    • Usual suspects: softmax, LayerNorm, sigmoid tails, add of two very different ranges. Lift them to 16-bit.
      • 
      
    • FP16 on HTP overflows above ~65k. Watch un-normalised activations.
      • 
    
    
    
    Reproducibility checklist
      
      
    • Pin QAIRT version, HTP arch and soc_model in artifact metadata.
      • 
      
    • Store DLC and encodings next to the binary so you can rebuild.
      • 
      
    • Build binaries in Docker on x86 Linux, never on a dev laptop.
      • 
      
    • Record device firmware: the DSP image changes behaviour too.
      • 
      
    • Use the QNN Saver backend to capture a failing API sequence and replay it.
      •
